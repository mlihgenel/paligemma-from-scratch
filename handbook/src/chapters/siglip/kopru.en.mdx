# The bridge: how the image enters the language model

<p className="lead">The vision side produced 256 vectors. The language model expects a sequence of tokens. The bridge has three steps. The <b>processor</b> builds a sequence that leaves 256 empty slots for the image. The <b>projector</b> moves the image vectors to the language model's size. The <b>merge</b> writes those vectors into the empty slots. By the end of this page the sequence Gemma sees is ready.</p>

## 3. Merging: two sources, one sequence

Every position of the sequence Gemma sees comes from one of two sources: text tokens from the embedding **table**, image tokens from the **projector**. `_merge_input_ids_with_image_features` stitches them together. Step by step with a small example (T = 10, D = 4):

<Scrolly label="_merge_input_ids_with_image_features" figure={(s) => <MergeScatter step={s} />}>
<Step>**`input_ids`**: the 10 ids from the processor. The image positions hold the `<image>` = 257152 placeholder. For the demo we put 2 `<pad>` tokens at the end (the project's model currently rejects padding).</Step>
<Step>**`inputs_embeds`**: first **all** ids go through the embedding table, `<image>` included. Those columns will be thrown away in a moment. In the real checkpoint the `<image>` row has a norm of ≈ 7.3, but it is never used. The text rows are multiplied by √d at this point (<Link to="/gemma/sqrt-d">4.3</Link>).</Step>
<Step>**Three masks**, each <S s="B, T" />: text, image, pad. They exclude each other and together cover the whole sequence.</Step>
<Step>**`unsqueeze(-1).expand`**: <S s="B, T" /> → <S s="B, T, 1" /> → <S s="B, T, D" />. Each mask cell is split into D sub-cells. `expand` copies no memory, it repeats the same value along D as a view.</Step>
<Step>**`torch.where` (text)**: the (scaled) text columns are copied from the **same position** into `final_embedding`, which starts as zeros. `where` picks element by element, so both sources must have the same shape. The blue block waiting on the right is the image features: <S s="B, 4, D" />.</Step>
<Step>**`masked_scatter` (image)**: the image features are <S s="B, 4, D" />, the target is <S s="B, 10, D" />. Different shapes, so `where` cannot be used. `masked_scatter` **flattens the source and pours it in order** into the True positions: v0 into the first `<image>`, v1 into the second… Watch the columns flow into place one by one.</Step>
<Step>**`torch.where` (pad → 0)**: the pad positions were already zero; this line is a safeguard. The result, <S s="B, T, D" />, goes to Gemma.</Step>
</Scrolly>

<CodeWalk file="paligemma.py" symbol="PaliGemmaForConditionalGeneration._merge_input_ids_with_image_features" notes={[

<Predict q="What would happen if the prompt had 255 <image> tokens instead of 256?">
<code>masked_scatter</code> would use the first 255 × 2048 elements of the source and <b>not raise</b>: the last image vector would be silently dropped. With 257 the source would run out and you would get an error. That is why newer HF versions compare the counts in <code>get_placeholder_mask</code> and raise. This project's code has no such check; as long as the processor is right, it is not a problem.
</Predict>

## 5. Who sees whom: the prefix-LM mask

The sequence is now one piece, but what really makes image and text **talk** is attention. PaliGemma's attention has one rule: the prefix (image + prompt) can look in every direction within itself, while the generated answer only looks at the past.

<Fig caption={<><b>PaliGemma's mask.</b> Row: the token that looks, column: the token looked at. Add generated tokens with the slider, and compare with a fully causal mask using the tabs.</>}>
<PrefixMask />
</Fig>

<Callout kind="neden" title="Why full attention in the prefix?">
PaliGemma paper (§5.2): letting the image tokens see the prompt, i.e. "what is being asked", shapes the image representation for the task. With a fully causal mask the first image token sees nothing and the last image token cannot see the prompt. The prefix is given in full anyway, so there is no risk of leaking information from the future. The causal constraint is only needed for the part the model <i>generates</i>.
</Callout>

<Note label="In the code">The mask is built by <code>make_prefix_lm_mask(total_len, prefix_len, …)</code>, and the rule is one line: <b><code>i</code> may look at <code>j</code> ⇔ <code>j &lt; prefix_len</code> or <code>j ≤ i</code></b>. It starts from the causal mask and opens the prefix columns with <code>mask[:, :prefix_len] = 0</code>. <code>PaliGemma.forward</code> builds it and passes it to <code>GemmaModel</code>, which builds a causal mask if none is given (<Link to="/gemma/attention">4.11</Link>). Uncached generation appends answer tokens to the input and keeps <code>prefix_len</code> at the length of the original prompt. With the KV cache the prefix is processed only once (<Link to="/gemma/kv-cache">4.12</Link>).</Note>

<Callout kind="dikkat" title="In HF the prefix is not always bidirectional">
HF only makes the prefix bidirectional when <code>token_type_ids</code> is given. The processor produces it when an answer (suffix) is provided. Run with just image + prompt and there is no <code>token_type_ids</code>, so HF's mask becomes <b>fully causal</b>. The paper and the original code keep the prefix bidirectional at inference too. This project's model does that, and when HF is given <code>token_type_ids = 0</code> for comparison, the logits match exactly. Without it the difference is large (~8–10 on a small random model).
</Callout>

## Concept questions

<ConceptQ n={1} q="Why is the bridge a single linear layer?">
The PaliGemma paper (§5.5, connector design) compares a linear projection with an MLP connector and finds no meaningful difference, so it picks the simpler one. The reason: SigLIP's representation is already aligned with language (<Link to="/big-picture">2.1</Link>) and Gemma is strong. The two sides do the heavy lifting, and the bridge mostly just has to match the sizes. PaliGemma also freezes nothing during training: SigLIP and Gemma are tuned together, so the flexibility comes from both sides.
</ConceptQ>
<ConceptQ n={2} q="The image tokens do not come from the embedding table. Where is the embedding of the <image> token, and how is it replaced?">
<code>&lt;image&gt;</code> (id 257152) is a real token in the vocabulary and has a row in the table. First all <code>input_ids</code> go through the table, the &lt;image&gt; row included. Then <code>masked_scatter</code> in <code>_merge_input_ids_with_image_features</code> writes the (unscaled) projector output over those positions in order. The table row of &lt;image&gt; ends up never being used (the merge animation above).
</ConceptQ>
<ConceptQ n={3} q="What is the role of the \n appended to the prompt?">
PaliGemma is a prefix-LM: the prefix (image + prompt) has full attention, the suffix (answer) is causal. During training <code>\n</code> marked where the prefix ends. The model learned that the token after <code>\n</code> is the first token of the answer. Without it the model may try to continue the prompt. This separator also sets the boundary of the prefix mask.
</ConceptQ>
