# lm_head and weight tying

<p className="lead">The model's largest single matrix does two jobs: at the input it turns tokens into vectors, at the output it turns vectors into token scores. Not two <code>nn.Linear</code>s, but two <b>names</b> for one object.</p>

## One plate, two roles

<Scrolly label="One matrix, two jobs" figure={(s) => <TyingScene step={s} />}>
<Step>
**The table.** A single matrix of size <S s="V, D" ax="V,D" />: each row is a token's vector. 10 × 6 here, 257216 × 2048 in reality (527 M numbers). Hover the cubes to see their values.
</Step>
<Step>
**At the input: a dictionary.** `embed_tokens(id)` computes nothing: if id = 3 it takes row 3 and hands it to the stream. Watch the copy of the row fly to the left. This is indexing: <span className="mono">W[ids]</span>.
</Step>
<Step>
**At the output: a yardstick.** The last hidden state (orange) is dotted with every row of the **same** matrix: <span className="mono">logits = norm(h) @ Wᵀ</span>. The bars on the right are the logits. The longest (highlighted) is the row most similar to h, i.e. the next token.
</Step>
<Step>
**Two roles, one object.** The tensor that picks rows at the input is the same one that produces scores at the output. The model learns a token's embedding as the direction the stream has to reach when it wants to produce that token. On top of that, 527 M parameters are saved.
</Step>
</Scrolly>

## What does "the same object" mean in Python?

<Fig caption={<><b>Two names, one object.</b> Step through the tabs. The fourth one shows a common mistake.</>}>
<ObjectDiagram />
</Fig>

<Predict q="After tie_weights, how many [257216, 2048] tensors does model.parameters() return? How many keys does state_dict() have?">
<code>parameters()</code> returns <b>one</b>: it does not count the same object twice. <code>state_dict()</code> returns <b>two</b> keys (<code>model.embed_tokens.weight</code> and <code>lm_head.weight</code>), both pointing to the same memory. Measured on the toy model: 9.70 M parameters before tying, 9.57 M after. The difference is 512 × 256 = 131 K, exactly one table.
</Predict>

## The real checkpoint has no lm_head

<Fig caption={<><b>A note on loading weights.</b> Google's checkpoint stores the tied tensor once. The model's <code>state_dict()</code> produces two keys.</>}>
<TyingFacts />
</Fig>

<Callout kind="dikkat" title="When loading the real weights">
Calling <code>load_state_dict</code> directly with the checkpoint file and the default <code>strict=True</code> would raise <b>"missing key: language_model.lm_head.weight"</b>. The project's <code>load_hf_weights</code> takes the weights from the HF model's <code>state_dict()</code> (where the tied tensor shows up under both keys), translates the names, raises if the key sets do not match exactly, and calls <code>tie_weights()</code> again at the end. After loading, <code>lm_head.weight is embed_tokens.weight</code> is still True.
</Callout>

## logits.float(): memory and precision

<Fig caption={<><b>The size of the logits tensor.</b> T × 257216 grows fast. At 896 px, float32 logits for the whole sequence exceed 4 GB. Generation only needs the logits of the last position, which is why HF has a <code>logits_to_keep</code> parameter.</>}>
<LogitMemory />
</Fig>

<Fig caption={<><b>How coarse bf16 logits are.</b> Logits are typically in the range 10–40. There, bf16's step size is 0.0625–0.25. In softmax, probabilities scale with the exponential of logit differences, so a single rounding can shift a probability by 6–28%. In greedy decoding, if two candidates are close, even their order can change.</>}>
<LogitPrecision />
</Fig>

<Impact from="gemma.py: return logits.float()" to="greedy decode: token-for-token match with HF">
With the real weights, the project's greedy generation matches HF token for token. Both take the argmax over float32 logits. With bf16 logits, candidates with equal scores could pick different tokens.
</Impact>
