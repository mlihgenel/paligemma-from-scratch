# MQA and repeat_kv

<p className="lead">Gemma 2B's attention has 8 query heads but only <b>1</b> head for keys and values. The saving comes from memory, not compute. <code>repeat_kv</code> is a small function that "expands" the single KV head to the 8 query heads at compute time.</p>

## Heads and sharing

In classic multi-head attention Q, K and V all have the same number of heads: each head produces its own query, key and value. Gemma 2B does this instead:

- **Q**: 8 heads of 256 dims each. `q_proj`: 2048 → 8 × 256.
- **K and V**: 1 head. `k_proj`, `v_proj`: 2048 → 1 × 256.

This is called **multi-query attention** (MQA). The cases in between (e.g. 2 KV heads for 8 Q heads) are **grouped-query attention** (GQA). All of them are settings of one idea: <span className="mono">n_rep = n_heads / n_kv_heads</span> Q heads share one KV head.

## Where is the saving?

At first glance one might think "K and V got smaller, so the matrix multiplications got smaller". But every Q head still produces a full score table: 8 <span className="mono">q @ kᵀ</span> products for 8 heads. The number of operations for the scores stays the same under MQA.

The gain is in two places:

1. **Parameters**: `k_proj` and `v_proj` are 8× smaller.
2. **KV cache**: when generating text, K and V are **stored** for every token in every layer. What is stored is proportional to the number of KV heads: 8× less under MQA.

<KvCacheSize />
</Fig>

<Predict q="Q keeps 8 heads but K and V drop to 1. How does the number of operations for the scores (q @ kᵀ) compare with MHA?" hint="Every Q head still produces a full T × T score table.">
<b>The same</b>. 8 heads × T × T × 256 multiply-adds, whatever the number of K heads. K having one head only means that head is <i>read</i> 8 times. That is why the real gain of GQA/MQA is <b>memory and memory traffic</b> (especially the KV cache), not compute.
</Predict>

## repeat_kv

The scores are computed with `q @ k.transpose(2, 3)`. For that matmul, Q and K must have matching head counts. So just before the scores, each KV head is **repeated** once per Q head that uses it.

## Axis order: a silent bug

There are two possible orders for the merge, and both give the same shape. One is the layout the weights expect; the other connects the Q heads to the KV heads alternately. The difference only shows when n_kv &gt; 1. Gemma 2B has n_kv = 1, so this bug would <b>go unnoticed</b> there, but it would silently break Gemma 2 (4 KV heads). That is why the check tries GQA as well as MQA.

<BreakIt title="merge the axes in the order (n_rep, n_kv) instead of (n_kv, n_rep) (8 Q, 2 KV heads)"
  good={`x = x[:, :, None, :, :].expand(B, n_kv, n_rep, T, hd)   # ← the new axis to the RIGHT of n_kv
x.reshape(B, n_kv * n_rep, T, hd)             # Q0-Q3 → KV0, Q4-Q7 → KV1`}
  bad={`x = x[:, None, :, :, :].expand(B, n_rep, n_kv, T, hd)   # ← the new axis to the LEFT of n_kv
x.reshape(B, n_rep * n_kv, T, hd)             # Q0 → KV0, Q1 → KV1, Q2 → KV0, …`}
  result={(b) => <OrderMap wrong={b} />} />

## When does expand copy?

`expand` copies no data, while `reshape` returns a view or a copy depending on the axes being merged. Measured with the project's `repeat_kv`:

<Fig caption={<><b>Nothing is copied under MQA, a copy is made under GQA.</b> With n_kv = 1 one of the two merged axes already has length 1, so <code>reshape</code> can return a view without allocating memory. With n_kv = 2 the (n_kv, n_rep) axes are merged by copying, because the memory layout is not contiguous. In both cases the <b>stored</b> K/V are small, because the repeat only happens at compute time.</>}>
<ExpandMemory />
</Fig>

<ConceptQ n={3} q="What does GQA/MQA reduce: compute or memory?">
<b>Memory</b>: the KV cache and the K/V projection weights. The scores are still computed for every Q head. During text generation (one token per step) the bottleneck is not compute anyway, but <i>reading</i> the KV cache from memory. MQA reduces that reading, so generation gets faster.
</ConceptQ>

<Callout kind="dikkat" title="head_dim comes from the config">
In Gemma 2B, <code>8 × 256 = 2048 = hidden_size</code>, so computing <code>head_dim</code> as <code>hidden_size / n_heads</code> happens to be right. In Gemma 2 it is not (<code>8 × 256 ≠ 2304</code>). That is why <code>GemmaAttention</code> reads <code>head_dim</code> from the config and <code>o_proj</code>'s input is <code>n_heads × head_dim</code>. The next page has <Link to="/gemma/attention">attention as a whole</Link>.
</Callout>
